O que é Arquitetura de Sistemas?

Entendendo a Separação de Conceitos (Separation of Concerns - SoC).

Explicação Descomplicada

Por que organizamos o código em camadas?

Imagine tentar construir uma casa onde os canos de água passam por dentro da fiação elétrica e as lâmpadas estão coladas diretamente no telhado sem nenhum interruptor. Se uma lâmpada queimar, você precisa destruir o telhado!

Em software, quando misturamos tela, banco de dados e regras de cálculo no mesmo arquivo, criamos um "Código Espaguete". A Arquitetura de Sistemas define como dividimos o código em blocos organizados, onde cada parte faz apenas o seu trabalho.

O Princípio SoC (Separation of Concerns)

O princípio de Separação de Conceitos (SoC) dita que um sistema deve ser dividido em seções distintas, para que cada seção aborde uma responsabilidade específica.

Fácil de manter e consertar erros
Permite trabalho em equipe paralelo
Reutilização e testabilidade de código

O Padrão MVC em Profundidade

Model - View - Controller: A arquitetura mais famosa do desenvolvimento de software.

A Analogia Completa do Restaurante 🍔

Para entender o MVC de primeira, pense em como funciona o atendimento em um restaurante bem organizado:

VIEW (Visão) 📋

O Cardápio & A Mesa

É o que o cliente enxerga. O cardápio mostra as opções e o prato pronto é servido na mesa. A View não sabe cozinhar, ela apenas exibe as informações bonito para o usuário interagir.

CONTROLLER 🤵

O Garçom (Intermediador)

O garçom annotation recebe o pedido do cliente, leva até a cozinha, espera o prato ficar pronto e traz de volta para a mesa. Ele orquestra o fluxo sem cozinhar e sem desenhar o cardápio.

MODEL (Modelo) 👨‍🍳

A Cozinha & A Despensa

É onde fica a inteligência! A cozinha possui as receitas (regras de negócio), os ingredientes e consulta a despensa (banco de dados). A cozinha prepara a refeição e valida se há ingredientes disponíveis.

M

Model em Detalhes

  • Entidades do Sistema: Representa os dados (ex: Usuario, Produto).
  • Regras de Negócio: Cálculos de descontos, validações de CPF, regras de estoque.
  • Mapeamento de Dados (ORM/SQL): Comunica-se com o Banco de Dados para buscar, salvar e atualizar registros.
V

View em Detalhes

  • Interface com o Usuário (UI): HTML, CSS, Botões, Formulários e Telas.
  • Template Engines: Substitui variáveis no HTML com dados trazidos do backend (ex: Blade, EJS, Thymeleaf).
  • Zero Regras de Negócio: A View apenas exibe dados, nunca calcula impostos nem consulta o banco diretamente.
C

Controller em Detalhes

  • Recepção de Requisições: Escuta rotas HTTP (GET /produtos, POST /login, DELETE /item).
  • Tratamento de Dados (DTOs): Coleta os campos do formulário e valida se foram preenchidos.
  • Seleção de Resposta: Decidir qual View renderizar ou responder com JSON no caso de APIs.

Fluxo de Dados Passo a Passo no MVC

Evolução do MVC no Mercado Atual

MVC Monolítico/Server-Side (Laravel, Django, Spring MVC): O servidor gera o HTML completo na View e entrega pronto para o navegador.

MVC com APIs REST + SPA (React/Vue/Angular + Node/Java): O Controller backend não devolve HTML (View), ele devolve apenas dados puros em JSON. A View passa a rodar inteiramente no navegador do cliente através de um framework JavaScript!

Exemplo Prático: Pedido de Lanchonete

Como as 3 camadas funcionam em código real de uma aplicação.

Caso Prático: Processar Pedido de Lanche Código Ilustrativo

1. Model (Pedido.js)

Valida se há lanches no estoque e calcula o valor total com imposto no Banco de Dados.

class PedidoModel {
  async criarPedido(itens) {
    // 1. Regra de Negócio
    if (itens.length === 0) {
      throw new Error("Carrinho vazio!");
    }
    
    let total = 0;
    for (let item of itens) {
      total += item.preco;
    }

    // 2. Salva no Banco SQL
    return await DB.salvar({
      itens,
      total,
      status: 'PENDENTE'
    });
  }
}

2. Controller (PedidoController.js)

Recebe a chamada da Rota HTTP, invoca o Model e define qual View responder.

class PedidoController {
  async fazerPedido(req, res) {
    try {
      const itens = req.body.itens;
      
      // Chama o Model
      const pedido = await PedidoModel.criarPedido(itens);
      
      // Chama a View com sucesso
      res.render('sucessoView', { pedido });
    } catch (erro) {
      res.render('erroView', { mensagem: erro.message });
    }
  }
}

3. View (sucessoView.html)

Recebe os dados prontos enviados pelo Controller e apenas exibe na tela para o cliente.

<div class="card-sucesso">
  <h1>Pedido Confirmado!</h1>
  <p>Número do Pedido: {{pedido.id}}</p>
  <p>Total a Pagar: R$ {{pedido.total}}</p>
  <span class="badge">{{pedido.status}}</span>
</div>

Guia Completo de Diagramas UML

Unified Modeling Language — A linguagem padrão de engenharia de software.

O que é UML e por que usar? 📐

Assim como engenheiros civis usam plantas baixas padronizadas no mundo inteiro para desenhar prédios, os engenheiros de software utilizam a UML (Linguagem de Modelagem Unificada). Ela evita que desenvolvedores interpretem os requisitos do projeto de formas totalmente diferentes.

🏛️ Diagramas Estruturais

Modelam a parte estática do sistema: a estrutura de dados, classes, atributos, objetos e como os pacotes estão organizados fisicamente.

🔄 Diagramas Comportamentais

Modelam a parte dinâmica do sistema: como os dados fluem ao longo do tempo, as respostas aos eventos e a ordem das mensagens trocadas.

Comportamental

1. Diagrama de Casos de Uso (Use Case)

Fase do Projeto: Levantamento de Requisitos

Mapeia QUEM (Atores) interage com o sistema e O QUE (Casos de Uso) eles conseguem fazer. Não mostra detalhes técnicos ou código.

👤 Ator: Boneco que representa o usuário ou outro sistema externo.
«include» (Obrigatório): O caso de uso A SEMPRE executa o caso de uso B. Ex: Sacar inclui obrigatoriamente Validar Senha.
«extend» (Opcional): O caso de uso B só executa em momentos específicos. Ex: Imprimir comprovante é opcional.
🎯 Aplicabilidade Prática:

Usado nas reuniões iniciais com o cliente para fechar o escopo do contrato e entender todas as funcionalidades que o software precisa ter.

Estrutural

2. Diagrama de Classes

Fase do Projeto: Modelagem Orientada a Objetos

O diagrama mais famoso da UML. Define os moldes dos objetos, seus atributos, métodos e como se conectam.

🔒 Visibilidade de Atributos e Métodos:

+ Público (Acessível de qualquer lugar)

- Privado (Acessível só dentro da própria classe)

# Protegido (Acessível só pela classe e suas herdeiras)

🔗 Tipos de Relacionamento:

♦️ Composição (Forte): O filho morre se o pai for apagado. Ex: Pedido e ItemPedido.

♢ Agregação (Fraca): O filho sobrevive sem o pai. Ex: Carrinho e Produto.

🔺 Herança: Uma classe herda características de outra.

🎯 Aplicabilidade Prática:

Servir de mapa direto para os programadores criarem as tabelas no Banco de Dados e os arquivos de código no Java, C#, PHP ou Python.

Comportamental

3. Diagrama de Sequência

Fase do Projeto: Design da Lógica do Sistema

Mostra a troca de mensagens entre os objetos ao longo do tempo, em ordem cronológica de cima para baixo.

➡️ Linhas de Vida (Lifelines): As colunas tracejadas indicam a existência do objeto no tempo.
🔲 Blocos alt e opt: Blocos retangulares em volta das setas que representam um if/else (ex: se a senha estiver errada).
🎯 Aplicabilidade Prática:

Essencial para entender processos complexos passo a passo (como a integração com o Gateway de Pagamento do Pix ou emissão de NFe).

Comportamental

4. Diagrama de Atividades

Fase do Projeto: Mapeamento de Regras de Negócio

Semelhante a um fluxograma. Mostra o passo a passo de um algoritmo ou processo de negócio, com decisões e execuções em paralelo.

◆ Losango de Decisão: Avalia uma condição boolean (Sim / Não).
➖ Barra Fork / Join: Divide o fluxo para executar 2 coisas ao mesmo tempo em paralelo (ex: enviar SMS e enviar Email).
🎯 Aplicabilidade Prática:

Excelente para conversar com analistas de negócio que não entendem código para validar a regra antes de programar.

Comportamental

5. Diagrama de Estado (State Machine)

Fase do Projeto: Modelagem de Ciclo de Vida de Entidades

Mostra todos os estados possíveis pelos quais um único objeto passa durante sua vida no sistema e quais eventos causam a mudança de estado.

🎯 Aplicabilidade Prática:

Crucial para gerenciar pedidos de e-commerce, status de chamados de suporte ou agendamentos de consultas médicas sem permitir transições proibidas (ex: não dá para entregar um pedido sem pagar).

Estrutural

6. Diagrama de Objetos

Fase do Projeto: Validação de Instâncias e Testes

Exibe uma fotografia instantânea do sistema em um determinado momento da execução, mostrando valores reais contidos dentro dos atributos de cada objeto.

📐 Diagrama de Classes (Abstrato) Classe Usuario { nome: String, idade: int }
📸 Diagrama de Objetos (Instância Real) usr1: Usuario { nome = "Carlos", idade = 28 }
🎯 Aplicabilidade Prática:

Ótimo para explicar aos alunos como a memória RAM armazena instâncias reais criadas pelo operador new do código.

Estrutural

7. Diagrama de Pacotes (Organização Modular)

Fase do Projeto: Organização da Arquitetura do Projeto

Organiza as classes do sistema em pastas (módulos/pacotes) e indica como um pacote de código depende do outro.

🎯 Aplicabilidade Prática:

Ideal para definir a estrutura de diretórios e namespaces do projeto antes de começar a programar.

Estratégias e dinâmicas de engajamento para aplicar em sala de aula.

Dinâmica Teatral em Sala (Padrão MVC)

Chame 3 alunos para a frente do quadro:

  • Aluno A (View): Pede um lanche e aguarda o prato.
  • Aluno B (Controller): O garçom que leva e traz bilhetes de papel.
  • Aluno C (Model): Fica de costas anotando os ingredientes no quadro (Banco SQL).

Perguntas Provocativas para o Quadro

  • "Se eu colocar um comando SQL dentro do HTML da minha View, qual princípio do SoC eu estou violando?"
  • "Qual a diferença entre colocar uma relação de Agregação e Composição em um sistema bancário?"
  • "Por que não desenhamos diagramas de casos de uso com telas de botões?"
